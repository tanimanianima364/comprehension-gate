# Kiro and Cursor support was dropped, and the per-host machinery with it

## What this change was for

The plugin supported five host configurations. Its entire surface is now the
context it injects, and two of those hosts cannot receive the part that
matters.

Cursor's prompt hook carries no context field at all, and its `preToolUse` is
registered `failClosed` — so the one event this design leans on hardest could
not be used there without risking every tool call in the session, and the
reminder could only ever reach the agent at session start. Kiro's rendering of
context on a tool event was never verified against a running host; the adapter
was written from vendor documentation.

Supporting them was not free. It cost three adapter templates, a renderer, a
mode argument threaded through every result, and a per-host shape for every
allow, every context injection, and every error — for hosts on which the gate
could not do the thing it now exists to do.

## The approach, and what it rejected

Keeping the adapters as unverified best-effort was the alternative, and the
honest version of that is what the README already said: "not verified live".
That is a reasonable position for a gate that *blocks*, because a host where
it silently does nothing merely loses enforcement. It is not reasonable for a
plugin whose only output is injected context: on a host that does not render
it, the plugin is not degraded, it is absent — and indistinguishable from a
working one.

Dropping only Cursor was considered, since Kiro's failure is unverified rather
than known. It was rejected because the two share the whole cost: the mode
argument, the per-host result shapes, and the renderer exist for either of
them, so removing one leaves all of the machinery and half the benefit.

The `Stop` registration went at the same time. It had been kept through the
last three changes so the live-verified adapter wiring would not be disturbed,
but on the two remaining hosts it had already been a plain allow since the
turn hold was removed; the hosts it still did something for were exactly these
two. The event is still answered if it arrives, because an installed copy
carrying the old configuration must not be told its event is unrecognized.

## How it is built

`handleHook(input)` lost its `mode` parameter and every branch that read it.
One host shape remains — `hookSpecificOutput.additionalContext` — so
`contextResult` has no alternatives to choose between, and `quietResult`,
`toolAllowResult` and `stopAllowResult` collapsed into `allowResult`. The
event names Cursor and Kiro spell differently (`agentSpawn`,
`beforeSubmitPrompt`, `agentStop`) are gone, and the recognized set is a plain
`Set` of the five Claude Code spellings.

`core/command.mjs` existed only to build adapter bootstrap commands and is
deleted with them, along with `scripts/render-adapter.mjs` and the two
`render:*` package scripts. `toolPaths` no longer reads an `operations` list,
which was Kiro's payload shape; `file_path`, `filePath`, `path` and
`notebook_path` remain, as does the Codex `apply_patch` envelope.

What is left is two hosts that share one `hooks/hooks.json`, and about 870
lines of core.

One operational consequence: the hook command definitions change, and Codex
will not run a hook whose definition changed until it is approved again. An
update therefore needs `/hooks` re-approval in an interactive session, which
the README now says.
